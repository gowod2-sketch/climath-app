### 왜 0인가 — 근본 원인

기존 형식은 `n = 1..12` 산점도로 **수열의 n→∞ 거동**을 인코딩한다. 기존 팁 22개의 `oneline`은 전부 극한·수렴·발산·부분합 문맥에 묶여 있다.

덧셈정리 단원에는 **극한이 한 개도 없다.** 22개 공식 전부가 각에 대한 항등식이다. 그래서 재사용도 신규도 불가능하다. `mathuit-tip-graph` SKILL이 "표현 불가" 예시로 직접 지목한 "각의 항등식 — 삼각함수 덧셈정리, 배각공식"이 이 단원의 **전부**다.

`oscillate`(진동)가 삼각함수와 겉보기에 가까워 재사용을 검토했으나, 현재 `oneline`이 "수렴도 아니고 oo, -oo 로도 가지 않는 **발산**"이다. 삼각함수의 주기성에 이 팁을 붙이면 학생은 삼각함수를 발산 개념으로 각인한다. **재사용도 기존 확장도 부적합**으로 판정했다 (확장하면 c01·c02 등 기존 개념의 문맥이 깨진다).

### sin / cos / tan 표기 문제 (프로브 목적 2, 질문 4)

**심각도: 중 — 우회 가능하고, 불가능한 지점은 없다. 단 우회 규칙 3개가 강제된다.**

`build.py` 코드 확인 결과:

- **수식 안(`$$`)은 문제 없다.** `ROMAN_WORDS = {'lim','log','sin','cos','tan','ln','max','min'}` — `sin`/`cos`/`tan` 모두 이미 로만체로 처리된다. 22개 공식 전부 수식 쪽은 그대로 쓸 수 있다.
- **본문은 깨진다.** `prose()`의 `\b([A-Za-z])(_...)?` 는 단어 경계의 **한 글자만** 잡으므로 `sin` → `s`만 이탤릭, `in`은 평문으로 남는다. SKILL 문서의 설명과 코드가 일치한다.

우회 방법 (concept-author에게 강제할 규칙):

1. **본문에서는 우리말로만 쓴다** — 사인, 코사인, 탄젠트. `sin A` 같은 표기를 본문에 절대 넣지 않는다. 특정 식을 가리켜야 하면 풀어 쓴다: "두 각의 합의 사인", "A의 사인과 B의 코사인의 곱".
2. **본문에 제곱을 쓰지 않는다** — `prose()`는 `^`를 캐럿 그대로 출력한다. `sin^2 A` 는 본문에서 "사인의 제곱"으로 쓴다. 반각 3개 개념이 여기 걸린다.
3. **θ를 쓰지 않는다 — 하드 블로커.** `SYM` 목록에 `alpha`, `beta`만 있고 **`theta`가 없다.** 명세 3️⃣ 반각공식은 θ로 쓰여 있는데, 그대로 옮기면 수식 안에서도 `theta` 다섯 글자가 이탤릭으로 흩어져 나온다. 아래 개념 목록에서는 **θ를 A로 바꿔** 표기했다(1️⃣2️⃣와 문자가 통일되는 부수 효과도 있다). `alpha`(α)로 바꾸는 선택지도 있으나 배각공식과 문자가 어긋난다.

서술이 성립하는가 — **성립한다.** 오히려 이 단원은 우리말 서술이 잘 맞는다. 합→곱 4개는 "두 사인의 합 / 두 사인의 차 / 두 코사인의 합 / 두 코사인의 차"로 본문에서 서로 완전히 구분되고, 곱→합 4개도 "A의 사인과 B의 코사인의 곱" 대 "A의 코사인과 B의 사인의 곱"으로 구분된다. 길어지지만 애매해지지는 않는다.

부수적으로 확인한 것:
- 분수는 `\frac`이 없으므로 전부 `/` 한 줄 표기다. `tan(A+B) = (tan A + tan B)/(1 - tan A tan B)` 정도까지는 한 줄로 읽히지만, 곱→합의 `(1/2)[...]` 는 중첩 슬래시라 가독성 확인이 필요하다 (에스컬레이션 7).
- 대괄호 `[ ]` 는 `mathify`의 로만 문자 집합에 있으나 중괄호 `{ }` 는 없다. 곱→합 공식은 명세대로 대괄호를 쓴다.
- `°`(도) 는 지원되지 않는다. 75°, 45° 는 풀이 예제에만 나오고 예제는 어차피 제외 대상이다.

- c29~c31은 같은 좌변(`cos 2A`)의 세 형태다. 본문에서 "어느 형태를 언제 쓰는가"를 서로 다르게 써야 세 화면이 중복으로 보이지 않는다.

## 에스컬레이션

1. **unit 신설 — 사람 결정 필요.** 기존은 `I. 수열의 극한`, `II. 지수함수와 로그함수의 미분` 두 개뿐이다. 삼각함수의 덧셈정리는 어느 쪽에도 속하지 않으므로 unit 신설이 불가피하다. 표에는 교육과정(미적분) 단원명을 따라 **`III. 삼각함수의 미분`**을 채워 두었다. 대안은 명세 제목을 그대로 쓴 `III. 삼각함수의 덧셈정리`인데, 이 경우 이후 삼각함수의 극한·미분 명세가 들어올 때 unit을 또 만들거나 이름이 내용과 어긋난다. **앱 목차 구조가 바뀌는 결정이라 임의로 확정하지 않았다.**

2. **sec 4개 신설 — 사람 결정 필요.** `01 삼각함수의 덧셈정리` / `02 배각공식` / `03 반각공식` / `04 곱과 합의 변환`. 개념 배분은 6 / 5 / 3 / 8이다. 03(3개)이 얇아 `02 배각공식과 반각공식`으로 묶어 3개 sec으로 갈 수도 있다(6 / 8 / 8). 기존 sec의 개념 수(6~7개)와의 균형을 보면 묶는 쪽이 관례에 가깝다. **결정 필요.**

3. **파일 번호 충돌 — 확인 필요.** docs/03 인벤토리가 `c14`, `c17`~`c21`을 예약했으나 실제 파일은 `c13`, `c15`, `c16`만 존재한다. 이 프로브는 예약분을 피해 **`c22`부터, order 22부터** 잡았다. docs/03의 나머지 개념을 작성하지 않기로 하면 번호가 비고, 작성하면 그대로 맞는다. **docs/03 잔여 작업 여부 확인 필요** — 결정 후 이 표의 번호를 확정한다.

4. **팁 그래프 형식 확장 — 이 프로브의 핵심 제품 결정.** 위 "형식 확장 판단 근거" 절 전체가 근거다. 요지: 현행 유지 시 이 단원은 개념 22개 전부 팁 링크 0개로 출고된다. 옵션 (A) 현행 유지 / (B) 연속 곡선 렌더러 / (C) 단위원·각 합성 도형 / (D) `## graph` 필수 완화 + `## steps` 단독 팁 허용. **주의할 사실: (B)는 7개 중 `trigfunc` 1개만 구제하고, docs/03의 표현불가 4개는 거의 구제하지 못한다.** 두 단원을 함께 구제하는 것은 (D)이며 렌더러 신규 개발이 없어 비용도 가장 낮다. 다만 (D)는 `build.py`의 필수 블록 검사와 앱 팝업 렌더러를 모두 건드린다. **어느 옵션인지는 제품 결정이므로 판정하지 않았다.**

5. **`oscillate` 재사용 가부 — 판단이 갈릴 수 있음.** 삼각함수의 주기성과 `oscillate`(진동)는 표면적으로 가깝다. 나는 oneline이 "발산"으로 규정되어 있다는 이유로 재사용·확장 모두 부적합으로 판정했다. 만약 "주기함수도 포괄"하도록 oneline을 고치면 이 단원 22개 개념 중 삼각함수를 언급하는 전부에 링크를 붙일 수 있게 되지만, **c01·c02 등 수열의 극한 개념의 문맥이 함께 바뀐다.** 기존 팁 수정은 내 권한 밖이다. **결정 필요.**

6. **명세 원문 오류 — 작성자 확인 필요.** `docs/04` 56행: `$$A \to \frac{\theta}{2}$로 치환하면:` 가 `$$`로 열고 `$` 하나로 닫혀 있다. 이 줄은 어차피 유도 과정이라 개념에서 제외했지만, 명세 자체의 렌더가 깨진 상태다.

7. **θ 미지원 및 분수 가독성 — 확인 권고.** `build.py`의 `SYM`에 `alpha`, `beta`만 있고 `theta`가 없다. 반각 3개는 θ를 **A로 치환**해 표기했다. 원본 표기를 살리려면 `SYM`에 `theta` 추가가 필요하다(빌드 스크립트 변경). 함께: `\frac`이 없어 곱→합 4개가 `(1/2)[...]` 중첩 슬래시로 한 줄 렌더된다. 실제 화면에서 읽히는지 눈으로 확인이 필요하다.
