# 하네스 구축 참고점

다른 프로젝트에 에이전트 하네스를 만들 때 재사용할 수 있는 판단 기준입니다.
mathuit 콘텐츠 파이프라인 하네스를 만들며 실제로 걸린 것만 적었습니다 — 일반론은 넣지 않았습니다.

> 읽는 순서: 1~3은 **시작 전**, 4~7은 **설계 중**, 8~10은 **마무리**에 봅니다.

---

## 시작 전

### 1. 도구 가용성을 먼저 확인하라 — 조용한 폴백이 가장 위험하다

하네스 프레임워크는 대개 **에이전트 팀**(팀원 간 직접 통신)을 기본 모드로 가정합니다. 그런데 이 기능은 실험 플래그(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) 뒤에 있고, **원격/웹 세션에는 `TeamCreate` 도구 자체가 없을 수 있습니다.**

문제는 없을 때 에러가 안 난다는 겁니다. 조용히 단일 에이전트 실행으로 폴백하고, 산출물은 멀쩡히 나옵니다. "5명이 교차 검증한 결과"인 줄 알았는데 실은 한 명이 쓴 것 — 겉으로 구분이 안 됩니다.

**대응:** 설계 전에 `TeamCreate` 가용 여부를 확인하고, 없으면 처음부터 서브 에이전트(`Agent` 도구, GA) 모드로 설계하세요. 같은 '혼자'라도 **계획된 혼자와 사고로 혼자는 결과가 다릅니다.**

```
확인 방법: ToolSearch로 TeamCreate 검색 → 안 나오면 팀 모드 금지
```

### 2. 3자 하네스/플러그인은 실행 전에 감사하라

읽지 않은 코드를 돌리지 마세요. 최소 이 4가지:

| 점검 | 명령 | 무엇을 보나 |
|------|------|------------|
| 실행 코드 유무 | `find . -type f ! -name '*.md'` / `-perm -u+x` | 마크다운만인가, 스크립트가 있나 |
| 위험 패턴 | `grep -rniE 'rm -rf\|curl.*\|sh\|sudo\|token\|api[_-]?key\|\.env\|bypassPermissions'` | 자격증명 접근, 파괴적 명령 |
| 외부 네트워크 | `grep -rniE 'https?://'` | 원격 콘텐츠를 가져오면 프롬프트 인젝션 표면 |
| **문서 vs 실재** | 문서가 언급한 CI·파일이 실제 있는지 `ls` | 신뢰도 신호 |

마지막 항목이 의외로 중요합니다. `revfactory/harness`는 "Nightly CI가 호환성 파손을 24시간 내 핫픽스한다"는 **공개 SLA를 문서에 명시**했지만, `.github/workflows/` 디렉토리 자체가 없었습니다. 참조된 `docs/cost-controls.md`, `compatibility-matrix.md`도 부재. 문서상 약속일 뿐 자동 감시 장치가 없다는 뜻이므로, 업스트림 변경 시 방치될 수 있다고 가정하고 채택하세요.

### 3. 중간 산출물을 `.gitignore`에 **미리** 넣어라

하네스는 보통 `_workspace/`에 중간 산출물을 쓰고 "감사 추적용으로 보존"하라고 합니다. `.gitignore`에 없으면 그대로 커밋됩니다.

증거: **`revfactory/harness` 레포 자신이 `_workspace/` 6개 파일을 커밋해 놓았습니다.** 저자도 못 피했습니다. 나중에 지우는 것보다 한 줄 미리 넣는 게 압도적으로 쌉니다.

```gitignore
_workspace/
_workspace_prev/
```

## 설계 중

### 4. 객관적 합격선을 먼저 찾아라 — 없으면 만들어라

하네스의 품질은 **판정이 주관적이지 않은 게이트가 있느냐**로 갈립니다. mathuit에는 `build.py`가 있었습니다 — 문법이 틀리면 `sys.exit(1)`로 멈추고 배포가 차단됩니다.

이런 게이트가 있으면:
- 에이전트 하나에게 "게이트 통과"만 전담시킬 수 있습니다 (역할이 명확해짐)
- 하네스가 실제로 작동하는지 사람이 안 봐도 압니다
- 수정 루프의 종료 조건이 생깁니다

프로젝트에 게이트가 없으면 (린터·타입체크·테스트 무엇이든) **먼저 만드는 게 하네스보다 우선순위가 높습니다.**

### 5. "형식은 통과하는데 내용이 틀린" 구멍을 찾아라 — 거기가 하네스의 진짜 값어치다

게이트가 있어도 만능이 아닙니다. `build.py`는 팁 파일에 `## graph` 블록이 **있는지**만 검사하고, 그 그래프가 **말이 되는지**는 안 봅니다.

mathuit의 팁 그래프는 `n=1..12` 수열 산점도로 고정인데, 미분계수나 삼각함수 덧셈정리는 수열로 표현되지 않습니다. 에이전트가 그럴듯한 curve를 지어내면 **빌드는 통과하고, 학생은 틀린 그림으로 개념을 각인합니다. 아무도 모릅니다.**

이런 구멍을 찾아 **"모르면 만들지 말고 멈추고 보고하라"**를 명문화하는 것이 하네스가 만드는 실제 가치입니다. 틀린 산출물은 없는 산출물보다 나쁩니다.

찾는 법: 게이트가 검사하는 목록을 뽑고, 각 항목에 "이걸 통과시키면서 틀릴 수 있는 방법"을 물어보세요.

### 6. 검증 축을 분리하라 — 한 에이전트에 몰면 쉬운 쪽만 본다

mathuit에서는 두 축이 독립입니다:

| 축 | 담당 | 질문 |
|----|------|------|
| 형식 | `build-gate` | **돌아가는가** (스크립트가 답함) |
| 내용 | `math-reviewer` | **맞는가** (사람의 판단) |

빌드가 통과해도 수학이 틀릴 수 있고, 수학이 맞아도 빌드가 막힐 수 있습니다. 한 에이전트에게 둘 다 맡기면 **객관적으로 확인되는 쉬운 쪽만 보고 통과시킵니다.**

각 에이전트 정의에 "당신이 **보지 않는 것**"을 명시하세요. 책임 경계를 적어야 서로 미루지 않습니다.

### 7. 병렬 에이전트의 공유 계약을 하나로 못 박아라

`concept-author`와 `tip-author`는 동시 실행되고 서로의 산출물을 보지 않습니다. 개념 본문의 `[[id|글자]]` 링크와 팁 파일명이 어긋나면 빌드가 실패합니다.

해법은 **선행 단계가 계약을 확정하는 것**입니다. `spec-analyst`가 팁 id 목록을 먼저 못 박고, 두 저자는 그 표만 봅니다. 계약을 만드는 단계는 반드시 순차이고, 여기에 게이트를 둡니다.

병렬 설계에서 물어볼 질문: **"이 둘이 서로를 안 보고도 맞물리려면 무엇이 미리 확정돼야 하는가?"**

### 8. QA는 "존재 확인"이 아니라 "경계면 교차 비교"다

파일이 각각 멀쩡해도 **경계에서** 깨집니다. concept의 링크 id ↔ tip 파일명 불일치는 파일을 하나씩 읽어서는 절대 안 보입니다. 양쪽 목록을 뽑아 차집합을 구해야 보입니다.

```bash
grep -rhoE '\[\[[a-z0-9_]+' content/concept/ | sed 's/^\[\[//' | sort -u > used.txt
ls content/tip/ | sed 's/\.md$//' | sort -u > exist.txt
comm -23 used.txt exist.txt   # 링크했는데 파일 없음 → 실패 원인
comm -13 used.txt exist.txt   # 파일은 있는데 미사용 → 고아
```

QA 에이전트는 반드시 **스크립트를 실행할 수 있는 타입**이어야 합니다 (`general-purpose`). 읽기 전용 타입은 검증 스크립트를 못 돌려서 "훑어보고 괜찮아 보인다"로 끝납니다.

## 마무리

### 6-b. 축을 나누면 어느 축에도 안 속하는 항목이 생긴다 — 분리의 대가

검증을 "형식 vs 내용"으로 나눈 것은 옳았지만, 그 결과 **둘 다 아닌 항목이 무주공산**이 됐습니다. 이번에 드러난 것:

| 무주공산 항목 | 왜 아무도 안 보나 |
|---|---|
| 제목이 계획과 일치하는가 | 수학 오류 아님(내용 담당 밖) · 빌드 통과함(형식 담당 밖) |
| 계획된 파일이 실제로 생성됐는가 | 생성된 파일만 검토 대상이었다 |
| 스텝이 요소를 하나씩 켜는가 | 연출 품질 — 어느 축도 아니다 |

두 번째 항목이 실질적 피해를 냈습니다. 계획된 개념 하나가 승인 대기로 빠졌는데, **그 개념을 근거로 삼는 다른 개념이 순환 서술**이 됐습니다. 빌드는 "번호가 비었다"조차 말해주지 않고, 내용 검토자는 생성된 파일만 봅니다.

**대응:** 축을 나눈 뒤 **"이 항목은 누가 보는가"를 항목별로 한 번 훑으세요.** 답이 없는 것이 무주공산입니다. 대부분은 교차 대조 담당(빌드/QA 쪽)에 "빌드가 강제하지 않는 규약도 대조하라"로 붙이면 되고, 차단이 아니라 **보고**로 처리하면 충분합니다.

특히 **계획 대비 누락 대조**는 반드시 명시적으로 배정하세요. 산출물만 검토하는 체계는 "없는 것"을 구조적으로 못 봅니다.

### 8-b. 상류 에이전트가 하류의 영역을 침범하면 검증이 통째로 무너진다

파이프라인에서 선행 분석 에이전트가 **구현 세부까지 제안**하면, 후속 저자가 그것을 검증 없이 따릅니다. 상류의 실수가 그대로 산출물에 박히는데, **두 단계를 거쳤으니 검토된 것처럼 보입니다.** 실제로는 아무도 안 봤습니다.

실제 사례: `spec-analyst`가 "이 팁의 curve는 `150 - 90/n` 계열"이라고 제안했는데, 그 식은 화면에서 점이 **내려가는** 모양입니다. 대상 수열 `(1+1/n)^n`은 e로 **증가**하며 수렴하므로 방향이 반대였습니다. 판정만 하라고 했으면 나오지 않았을 오류입니다.

**대응:** 에이전트 정의에 "당신이 **하지 않는 것**"을 역할만큼 명확히 쓰세요. 그리고 하류 에이전트에게는 *"상류의 제안이 틀릴 수 있다. 검산 결과가 다르면 당신 것을 따르고 보고하라"*를 명시하세요.

### 8-c. 하네스 문서의 사실 오류는 실전 투입 전까지 안 보인다

스킬에 적은 규칙이 **실제 빌드 도구의 동작과 다를 수 있습니다.** 그럴듯하게 읽히기 때문에 리뷰로는 안 걸립니다. 실제로 파일을 만들어 보는 에이전트만 발견합니다.

이번에 발견된 것 (전부 `build.py` 소스로 재확인함):

| 스킬에 적었던 것 | 실제 |
|---|---|
| "`lim`/`log`는 자동 로만체" | **`$$` 안에서만** 참. 본문의 `ln a`는 `l`만 이탤릭이 되어 깨진다 |
| "지수는 `r^n`으로 쓴다" | 본문에서는 캐럿이 **문자 그대로** 렌더된다 (`prose()`가 `_`만 처리) |
| "첫 에러에서 멈춘다" | front matter·수식은 즉시 종료, **링크 검증은 누적 후 일괄 보고** |
| "문단은 각 2~4문장" | 기존 코퍼스는 **전부 p1이 1문장**. 규칙이 코퍼스와 모순 |
| (언급 없음) | front matter `title`은 변환을 타지 않아 수식 표기가 그대로 노출 |

**대응 두 가지.**
1. 에이전트 프롬프트에 **"규칙이 부족하거나 모호했던 지점을 솔직히 보고하라"**를 넣으세요. 산출물만 받으면 이 정보가 사라집니다. 이번 개선의 대부분이 이 항목에서 나왔습니다.
2. 에이전트가 지적한 것을 **곧이곧대로 믿지 말고 소스로 검증하세요.** 이번엔 5건 전부 맞았지만, 맞았다는 것도 확인해야 아는 사실입니다.

### 8-d. 참조 표는 에이전트가 검증 없이 믿는다

산문으로 쓴 규칙은 에이전트가 문맥에 비춰 걸러냅니다. **표는 다릅니다.** 조회 대상이라 의심받지 않고, 이름만 보고 행을 고릅니다.

실제 사례: curve 카탈로그의 행 이름 두 개가 서로 뒤바뀌어 있었습니다. 상류 에이전트가 "아래에서 수렴"이라는 **맞는 이름**의 행을 골랐고, 그 행에 **틀린 식**이 있었습니다. 에이전트는 문서를 정확히 따랐고 문서가 틀렸습니다. 다행히 하류 에이전트가 검산 규칙 덕에 잡아냈습니다.

**대응 두 가지.**
1. 표의 **모든 행을 실제로 실행해 검산**한 뒤 문서에 넣으세요. 손으로 쓴 룩업 테이블은 거의 항상 어딘가 틀립니다.
2. 표를 참조하는 에이전트에게 **"이름만 보고 고르지 말고 대입해 확인하라"**를 명시하세요. 검산 절차를 규칙으로 박아두면 상류 오류가 하류에서 걸립니다.

### 8-e. 두 번째 도메인에 프로브를 돌려라 — 과적합과 진짜 한계가 같이 드러난다

첫 도메인에서 잘 도는 하네스는 그 도메인에 맞춰 만든 것이라 잘 도는 게 당연합니다. **성격이 다른 두 번째 소재**에 분석 단계만 돌려 보세요. 파일을 만들지 않으니 비용이 적고, 두 가지가 한꺼번에 나옵니다.

이번 프로브에서 나온 것:
- **과적합 없음** — 개선된 판정 체계가 새 도메인에서 그대로 작동했습니다
- **형식의 진짜 한계** — 두 번째 단원은 개념 22개 전부가 팁 링크 0개였습니다. 첫 도메인에서는 "표현불가 비율 80%"였지만 기존 팁이 살아남아 가려져 있었습니다. 두 번째에서야 **총량이 0**인 경우가 존재한다는 게 보였습니다
- **하드 블로커** — 기호 테이블에 θ가 없어 해당 단원 일부를 아예 표기할 수 없다는 사실

세 번째 항목이 특히 중요합니다. 첫 도메인에만 있었으면 영영 안 보였을 제약이고, **제품 결정(형식을 확장할 것인가)의 근거가 여기서 나옵니다.**

### 9. description은 좁게 — 프레임워크의 "pushy" 지침을 그대로 따르지 마라

하네스 프레임워크는 스킬 description을 **적극적("pushy")**으로 쓰라고 합니다. 트리거가 보수적이라 안 불리는 걸 막으려는 의도입니다.

그런데 그대로 따르면 **무관한 작업 중에도 튀어나옵니다.** 저장소 여러 개를 오가는 세션에서 특히 나쁩니다.

**대응:** 트리거 조건에 범위 한정을 붙이세요.
```
"...에만 사용하고, 일반적인 {도메인} 질문이나 이 저장소 밖의 작업에는 사용하지 않는다"
```
그리고 should-NOT-trigger 쿼리를 3개 이상 직접 써보고 걸리는지 점검하세요. 경계가 모호한 쿼리("퀴즈 터치 이벤트 고쳐줘" — 같은 앱이지만 콘텐츠가 아님)가 좋은 테스트입니다.

### 10. 기존 자산을 반드시 읽어라 — 하네스는 빈 땅에 짓지 않는다

`docs/03`(지수·로그 미분)을 새 단원으로 취급할 뻔했습니다. 실제로는 기존 `c12`가 이미 `unit: II. 지수함수와 로그함수의 미분`으로 그 단원을 시작해 놓았고, order는 13부터여야 했습니다.

파일명과 디렉토리 구조만 보고 추측하면 이걸 놓칩니다. **기존 산출물의 메타데이터를 실제로 열어서** 명명 관례·번호 체계·진행 상태를 확인하세요. 선행 분석 에이전트의 첫 임무로 못 박는 게 좋습니다.

### 11. 비용 손잡이를 남겨라

프레임워크가 **모든 에이전트에 최고가 모델을 강제**하는 경우가 있습니다 (`revfactory/harness`는 `model: "opus"`를 예외 없이 요구). 팬아웃까지 겹치면 작업 하나에 5만~20만 토큰이 나갑니다.

전부 최고 모델이 필요하지는 않습니다. **판단이 필요한 에이전트**(수학 검증, 설계)와 **절차를 실행하는 에이전트**(스크립트 돌리고 에러 옮기기)를 구분하고, 후자는 내려도 됩니다. 최소한 어디를 내릴 수 있는지 문서에 남기세요.
