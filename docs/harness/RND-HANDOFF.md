# 하네스 R&D 인수인계 — 다른 프로젝트에 이식하기 위한 정리

**작성 목적:** 이 문서는 mathuit 콘텐츠 파이프라인 하네스를 운영하며 실전에서 검증한 패턴·안티패턴을 **도메인 무관하게 일반화**해, 다른 세션이 다른 프로젝트의 하네스를 구축할 때 그대로 시작점으로 쓸 수 있게 정리한 것이다. mathuit 고유 규칙(SYM 테이블, `## graph` 등)은 예시로만 남기고 원칙만 이식하라.

---

## 0. "하네스"란 무엇인가 — 메타 스킬 스펙

이 계정에는 `harness`라는 전역 메타 스킬이 설치돼 있다(`revfactory/harness` 플러그인, `/root/.claude/skills/harness/SKILL.md` + `references/*.md` 6개). **주의: 이 전역 설치는 컨테이너 로컬이라 세션 간 자동으로 이어지지 않는다** — 다른 세션·다른 환경에서 이 스킬을 쓰려면 그 세션이 속한 계정/환경에도 설치돼 있어야 트리거된다(플러그인 마켓플레이스 등록 여부 확인 필요). 이 문서가 그 스킬의 SKILL.md를 대체하지는 않는다 — 이 문서는 **그 스킬을 실제로 한 프로젝트에서 굴려본 뒤 나온 현장 교훈**이다.

메타 스킬의 핵심 뼈대:

- **산출물은 항상 두 종류로 분리한다.** `.claude/agents/{name}.md`(누가·역할·원칙·재호출 지침) + `.claude/skills/{name}/SKILL.md`(어떻게·규칙·판단 기준). 에이전트 정의 없이 프롬프트에 역할을 즉석으로 써넣는 것은 금지 — 다음 세션에서 재사용이 안 된다.
- **오케스트레이터는 스킬의 특수한 형태다.** "누가 언제 어떤 순서로" 를 정의하고, `_workspace/`를 통해 단계 간 산출물을 넘긴다.
- **실행 모드 3종:** 에이전트 팀(`TeamCreate`+`SendMessage`, 실시간 조율 필요할 때 기본값) / 서브 에이전트(`Agent` 도구 직접 호출, 결과만 반환하면 충분할 때) / 하이브리드(Phase별로 혼합).
  - **mathuit은 서브 에이전트 모드를 썼다** — 이 환경엔 팀 통신 도구가 아예 없었기 때문. 이건 "차선책"이 아니라 **재사용 가능한 대체 패턴**이다: 팀 도구가 없는 환경에서는 `_workspace/{phase}_{agent}_{artifact}.md` 파일 계약이 팀 통신을 완전히 대체할 수 있다. 서로 다른 에이전트가 서로를 안 보고도(concept-author와 tip-author가 서로의 산출물을 안 보고) 인벤토리 한 장만 계약으로 공유하면 병렬 실행이 성립한다.
- **CLAUDE.md엔 포인터만 남긴다.** 에이전트/스킬 목록·상세 규칙은 절대 CLAUDE.md에 중복 서술하지 않는다 — 트리거 규칙 + 변경 이력 표만.
- **하네스는 진화한다.** 매 실행 후 피드백을 에이전트/스킬/오케스트레이터/CLAUDE.md 중 어디에 반영할지 분류하고, 변경 이력에 남긴다.

## 1. mathuit에서 실제로 검증된 아키텍처 패턴

**5개 전문 에이전트 + 오케스트레이터 스킬, "생성→검증" × "팬아웃/팬인" 조합:**

| 에이전트 | 축 | 역할 |
|---|---|---|
| spec-analyst | 분해·판정 | 원본 명세를 작업 단위로 쪼개고 재사용/신규 판정만 내림 (구현 안 함) |
| concept-author / tip-author | 생성 (병렬) | 서로의 산출물을 안 보고 인벤토리만 보고 동시 작성 |
| math-reviewer | 검증-내용 | "맞는가"만 본다 |
| build-gate | 검증-형식 | "돌아가는가"만 본다 (스크립트 실행, 눈으로 추측 금지) |

일반화할 수 있는 4가지 설계 결정:

1. **판정과 구현의 권한을 분리하라.** 상류 에이전트(spec-analyst)가 "이 용어는 신규다"까지만 말하고 "그래프는 이렇게 그려라" 같은 구현 디테일을 제안하면, 하류가 검증 없이 그대로 따라가 **두 단계를 거쳤지만 아무도 실제로 검토하지 않은** 산출물이 나온다. 이건 예의 문제가 아니라 안전 설계다.
2. **검증은 반드시 두 축으로 쪼개서 병렬로 돌려라.** 형식(스크립트가 판정, 주관 없음) vs 내용(도메인 전문가가 판정, 주관 있음). 한 에이전트에 둘 다 맡기면 쉬운 축만 보고 통과시킨다.
3. **데이터 계약은 파일 하나로 좁혀라.** 병렬로 도는 두 저자가 서로를 안 봐도 되게 하려면, 공유 인터페이스(인벤토리 표)의 정확성이 그 뒤 전체 단계의 품질을 결정한다. 이 파일이 파이프라인의 진짜 스키마다.
4. **배포 게이트는 "판단"이 아니라 "규칙"으로 코드화하라.** "이거 배포해도 되나요"를 사람에게 묻지 않는다. 막아야 할 조건을 전부 코드로 나열하고, 걸리면 자동으로 막고 이유를 출력한다. 이렇게 하면 게이트 통과 여부에 대한 논쟁이 없어진다 — 조건을 없애거나 규칙을 바꾸는 논의만 남는다.

## 2. 재사용 가능한 안티패턴 (실전에서 걸렸던 것들, 일반화)

| # | 실제 사고 (mathuit) | 일반화된 교훈 |
|---|---|---|
| 1 | 그래프 없는 팁에 `curveFn('')`이 예외를 먹고 "항상 100을 반환"하는 가짜 함수로 대체돼, 없는 그래프 대신 **틀린 평평한 그래프**가 렌더됨 | **결측을 그럴듯한 기본값으로 채우지 마라.** 결측은 명시적 플래그(`nograph: true`)로 표현하고, 렌더러가 그 플래그로 분기하게 하라. 틀린 산출물은 빈 산출물보다 항상 나쁘다 — 특히 학습 콘텐츠·의사결정 지원처럼 "그럴듯해 보이는 것"이 신뢰를 얻는 도메인일수록. |
| 2 | 문자열 치환기(`syms()`)가 링크 파서보다 먼저 실행돼, 팁 id(`sumval`)가 치환 테이블의 부분 문자열(`sum`)과 겹쳐 링크가 **빌드는 통과한 채로 조용히 죽음** | **정규화/치환 파이프라인에서 식별자·구조는 치환보다 먼저 보호하라** (placeholder로 빼뒀다 나중에 복원). 그리고 식별자 네이밍 단계에서 "치환 테이블과 충돌하는 부분 문자열인가"를 사전 점검 항목으로 못박아라 — 사후에 찾으면 이미 배포됐을 수 있다. |
| 3 | "최신 산출물"을 `sorted(glob(...))[-1]`(파일명 알파벳 정렬)로 골라, 지난 라운드의 백업 파일이 알파벳상 뒤에 와서 최신으로 오판됨 | **"최신"은 항상 수정 시각(mtime)이나 명시적 버전 태그로 판단하라.** 파일명 정렬로 순서를 추정하는 코드는 백업/아카이브 관례가 하나라도 생기면 깨진다. |
| 4 | 소스(`content/*.md`)는 고쳤는데 빌드 산출물(`index.html`)을 재생성 후 커밋에 안 넣어, 배포될 뻔한 산출물이 예전 값 그대로였음 | **생성 파이프라인의 게이트에 "산출물이 최신 소스로 재생성된 것과 git상 동일한가"를 직접 diff로 검사하는 단계를 넣어라.** "빌드 스크립트를 실행했다"와 "그 결과가 커밋됐다"는 다른 사실이다. |
| 5 | 상태 파일(인벤토리)의 "에스컬레이션" 섹션을 파싱하는 정규식이 다음 섹션 경계를 안 잡아, 뒤에 오는 무관한 섹션까지 에스컬레이션으로 오인 | **상태/보고서 파일을 정규식으로 파싱할 땐 항상 "다음 헤더 앞까지"로 경계를 명시적으로 bound하라.** `(?=^## |\Z)` 류의 lookahead 없이 짠 파서는 문서 구조가 조금만 늘어나도 조용히 오작동한다. |
| 6 | 사람 승인이 필요한 항목(에스컬레이션)이 하나만 있어도 파이프라인 전체를 세워, 무관한 다른 작업까지 지연 | **에스컬레이션은 이진(전체 중단/전체 진행)이 아니라 "차단 범위 매트릭스"로 세분화하라.** 항목별로 "이게 막는 범위가 이 항목 하나인지 / 이 섹션 전체인지 / 전체 배치인지"를 미리 분류해두면, 사람 응답을 기다리는 동안에도 무관한 작업은 계속 진행된다. |
| 7 | 콘텐츠 빌드는 계속 초록불이었는데, 배포 대상 사이트가 git에 연결이 안 돼 있어 실제로는 12일간 아무것도 배포되지 않음 | **"완료"의 정의에 "산출물 검증 통과"뿐 아니라 "실제로 사용자에게 도달했는가" 확인 단계를 반드시 포함하라.** 파이프라인 성공과 배포 도달은 서로 다른 실패 축이다. |
| 8 | 에이전트가 재호출됐을 때 전면 재작성해버려, 이미 검증 통과한 부분(검산 끝난 수식 등)까지 바뀌어 이전 검토가 무효화됨 | **모든 에이전트 정의에 "재호출됐을 때" 절을 명시하라: 지적된 부분만 고치고, 검증 통과한 부분은 건드리지 말 것.** 이게 없으면 검토자는 "내가 본 문장이 그대로 있다"는 가정이 매번 깨진다. |
| 9 | 같은 빌드 에러가 반복돼도 자동 수정을 계속 시도 | **동일 실패 N회(예: 3회) 반복 시 자동 루프를 멈추고 사람에게 올려라.** 수렴하지 않는 자동 수정 루프는 시간만 태운다 — "회차 제한"을 에이전트 정의에 숫자로 박아둬라. |
| 10 | **가장 비쌌던 실수:** 코드 규칙(`## graph` 필수 → 선택)을 바꾸면서 스킬 문서는 그날 고쳤지만, **에이전트 정의(`.claude/agents/*.md`) 본문에 그 규칙이 직접 서술된 곳**(도입부 문장)은 3라운드가 지나도록 안 고쳐, 에이전트가 뒤집힌 지시를 계속 따름 | **한 규칙이 여러 파일에 중복 서술되는 구조라면, "규칙 변경 시 갱신해야 할 파일 체크리스트"를 오케스트레이터 스킬 안에 고정 항목으로 박아둬라.** 코드 → 스킬 문서 → **에이전트 정의 본문** → CLAUDE.md, 이 네 곳 모두. 스킬만 고치고 끝났다고 생각하는 게 가장 흔한 누락이다. |
| 11 | 사용자 데이터(필기·마지막 위치)를 페이지 인덱스로 저장해뒀다가, 콘텐츠 순서를 재배치하니 기존 사용자 데이터가 다른 개념으로 조용히 이동 | **"규모가 커질수록 되돌리는 비용이 비례하는" 결정(스키마·식별자·저장 키·번호체계)은 대량 생산 전에 확정하라.** 반대로 렌더러·연출·레이아웃처럼 규모와 무관한 것은 아무 때나 고쳐도 비용이 같다. 이 구분이 없으면 "지금 크기에서 한 번, 커진 뒤 또 한 번" 같은 마이그레이션을 반복하게 된다. 마이그레이션 자체를 설계할 때도 **"그 시점의 순서"를 스스로 고정해서 들고 있어야** 한다 — 옛 상태를 현재 기준으로 역산하면 재배치할 때마다 매핑이 다시 어긋난다. |
| 12 | 같은 브랜치에 다른 세션이 독립적으로 커밋을 push해 충돌 | **강제 push나 임의 병합 대신, 커밋 트레일러/타임스탬프로 출처를 감식 → 로컬 병합 테스트 → 빌드 통과 확인 → 그 다음에만 push.** 대화 세션 자체를 통합하는 기능은 없다는 것도 같이 인지하라 — git이 이미 실질적인 "통합 지점"이고, 세션은 그 위에서 갈아타는 창구일 뿐이다. |

## 3. 하네스 메타 스킬 자체에 제안할 개선 (아직 상류에 반영 안 됨)

이번 라운드의 교훈 중 일부는 mathuit 프로젝트 로컬 스킬에만 박혀 있고, `revfactory/harness` 메타 스킬 자체(모든 프로젝트에 재사용되는 상류)에는 아직 반영되지 않았다. 다음에 하네스를 새로 구축하는 세션은 이 갭을 참고해 메타 스킬 쪽에 직접 제안하는 것을 고려하라 (이 리포는 GitHub 접근 범위 밖이라 이번 세션에서는 로컬 문서 정리까지만 함):

- **"정의 파일 동기화 체크리스트"를 오케스트레이터 템플릿(`references/orchestrator-template.md`)의 표준 항목으로 넣을 것.** 지금은 Phase 7(하네스 진화)에 "피드백 반영 경로" 표가 있지만, "규칙 하나가 여러 파일에 중복 서술된다"는 사실 자체와 그 갱신 체크리스트는 명시돼 있지 않다.
- **재호출 지침(Phase 5-5)에 "검증 통과 부분 불변" 원칙을 구체 문구로 추가할 것.** 지금은 "이전 결과가 있으면 개선점 반영"이라고만 돼 있어, 전면 재작성을 막는 문구가 약하다.
- **"완료"의 정의에 도달 확인(배포/전달)을 포함할지 여부를 명시하는 원칙 하나를 추가할 것.** 지금 메타 스킬은 오케스트레이션까지만 다루고 배포는 도메인 몫으로 취급한다. 최소한 "이 하네스에서 완료란 무엇인가"를 Phase 1(도메인 분석)에서 확정하게 하는 질문 하나가 있으면 좋겠다.

## 4. 새 프로젝트에 하네스를 구축할 때 실전 체크리스트

harness 메타 스킬의 Phase 0~7을 그대로 따르되, 위 교훈을 다음 지점에 미리 박아 넣어라:

1. **Phase 1(도메인 분석)에서 "완료의 정의"를 먼저 확정하라** — 산출물 검증 통과인지, 실제 배포/전달 도달까지인지.
2. **Phase 2(팀 아키텍처)에서 실행 모드를 정할 때, 팀 통신 도구가 없는 환경이면 주저 말고 서브 에이전트 + `_workspace/` 파일 계약으로 가라.** 이건 차선책이 아니라 검증된 패턴이다.
3. **Phase 3(에이전트 정의)에서 모든 에이전트에 "재호출됐을 때" 절을 필수로 넣어라** — 지적된 부분만 고칠 것, 재시도 상한(3회) 명시.
4. **판정 에이전트와 구현 에이전트를 분리하고, 판정 에이전트의 출력에 구현 디테일이 새어나가지 않게 하라.**
5. **검증은 형식/내용 두 축으로 쪼개 병렬 실행하라.**
6. **배포·반영 게이트가 있다면 "규칙" 목록으로 코드화하고, 그 규칙 안에 다음을 반드시 포함하라:** 산출물-소스 동기화 diff 체크, 부분 출고(근거 사슬 단절) 체크, 미해결 에스컬레이션 체크, 미푸시 커밋 체크.
7. **"규칙 변경 시 갱신할 파일 목록"을 오케스트레이터 스킬 본문에 명시적으로 적어라** — 코드, 스킬, 에이전트 정의 본문, CLAUDE.md 포인터 전부.
8. **스키마·식별자·저장 키 같은 "규모 비례 비용" 결정은 대량 생산 착수 전에 확정하라.** 이미 대량 생산에 들어갔다면, 마이그레이션은 "그 시점의 순서"를 스스로 고정해서 보존하게 설계하라.

*이 문서는 mathuit 콘텐츠 하네스(회차 1~5 + R&D 스프린트 1~5)를 실제로 운영하며 나온 교훈을 일반화한 것이다. 원본 사례의 세부 구현(수식 렌더링, SYM 테이블 등)은 `mathuit/build.py`, `.claude/agents/*.md`, `.claude/skills/mathuit-*/SKILL.md`, `CLAUDE.md`의 변경 이력을 참조하라.*
