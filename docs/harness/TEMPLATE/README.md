# 하네스 뼈대 (재사용 템플릿)

다른 도메인에 에이전트 하네스를 세울 때 쓰는 뼈대입니다.
`{{중괄호}}` 부분만 도메인에 맞게 채우면 됩니다.

---

## 먼저 — 이 뼈대의 근거가 얼마나 튼튼한가

**정직하게 말하면 부분적으로만 튼튼합니다.** 두 종류가 섞여 있으니 구분해서 쓰세요.

### 🟢 근거 강함 — 에이전트의 성질에서 나온 것

도메인이 아니라 **LLM 자체의 행동**이라, 다른 업무에서도 같은 방식으로 나타납니다.
전부 실제 관측 + 소스 검증을 거쳤습니다.

| 발견 | 관측 |
|---|---|
| 선택지가 없으면 **값을 창작한다** | 판정 3단계만 주니 4번째 상황에서 비표준 값을 지어냄 |
| 지적이 하나여도 **전면 재작성하려 한다** | *"저자 에이전트는 통째로 다시 만드는 쪽이 일관성 있다고 느낀다"* (에이전트 자기 보고) |
| **참조 표는 검증 없이 믿는다** | 룩업 표 행 이름이 뒤바뀐 걸 그대로 따름. 산문 규칙은 문맥으로 걸러냄 |
| **문서의 사실 오류는 실전 전까지 안 보인다** | 리뷰로 5건 전부 못 걸렀고, 실제로 파일을 만든 에이전트가 전부 찾음 |
| **상류 제안은 하류에게 앵커가 된다** | 상류가 낸 틀린 값을, 검산 규칙이 없었다면 하류가 그대로 썼을 것 |
| 산출물만 검토하면 **"없는 것"을 못 본다** | 계획된 항목 누락이 아무 검증에도 안 걸림 |

### 🟡 근거 약함 — 구조에 대한 판단 (n=1)

**전부 하나의 도메인(수학 콘텐츠 파이프라인)에서 나왔습니다.** 그럴듯하지만 검증된 일반성은 없습니다.
아래 가정이 깨지면 해당 부분은 버리세요.

| 가정 | 안 맞는 신호 |
|---|---|
| **객관적 합격선이 존재한다** | 통과/실패를 스크립트가 판정할 수 없다 → 형식/내용 축 분리가 성립 안 함 |
| 작업이 **병렬 단위로 쪼개진다** | 앞 결과를 봐야 다음을 정할 수 있다 → 공유 계약 개념이 무의미 |
| 산출물이 **서로를 근거로 인용한다** | 각 산출물이 독립적이다 → 근거 사슬 점검 불필요 |
| 반복되는 **정형 작업**이다 | 매번 성격이 다르다 → 하네스보다 그때그때 지시가 낫다 |

**세 개 이상 안 맞으면 이 뼈대를 쓰지 마세요.** 역할만 나눈 껍데기가 되고, 조율 비용만 늘어납니다.

## 사용 순서

| 파일 | 언제 | 근거 밀도 |
|---|---|---|
| `01-SETUP.md` | 착수 전 — 환경 확인, 합격선 식별 | 🟢5 🟡1 |
| `02-AGENTS.md` | 역할 설계 + 에이전트 정의 템플릿 | 🟢7 🟡2 |
| `03-ORCHESTRATOR.md` | 워크플로우 + 게이트 배치 | 🟢1 🟡3 |
| `04-VERIFY.md` | 검증 설계 — **여기가 하네스의 값어치** | 🟢7 🟡2 |
| `05-OPERATE.md` | 실전 투입 후 개선 루프 | 🟢7 🟡1 |

`01`은 건너뛰지 마세요. 여기서 걸러야 할 것을 놓치면 뒤가 전부 헛돕니다.

**`03`이 가장 약합니다.** 워크플로우 구조(파이프라인 배치, 게이트 위치, 보류 단위)는 전부 한 도메인에서 나온 판단입니다. 다른 도메인에서는 Phase 구성이 달라질 수 있으니, `03`은 **참고 예시**로 보고 `01`·`04`·`05`를 규칙으로 삼으세요.

`02`와 `05`는 반대로 밀도가 높습니다 — 에이전트의 성질과 개선 방법은 도메인을 타지 않습니다.

- 회차별 경과와 실제 관측: `../SPRINT-LOG.md`
- 도메인 중립 교훈 20항목: `../LESSONS.md`

뼈대가 애매하면 `LESSONS.md`를 보세요. 왜 그렇게 하라는지가 거기 있습니다.
