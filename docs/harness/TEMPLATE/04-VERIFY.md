# 04 · 검증 설계

**여기가 하네스의 값어치입니다.** 생성만 하는 하네스는 프롬프트 하나와 다르지 않습니다.

> 이 문서의 상당 부분은 🟡 **객관적 합격선이 존재한다**는 가정 위에 있습니다.
> 합격선이 없는 도메인이면 "축 분리"를 버리고, 대신 **사람 검토 항목을 명시적으로 나열**하는 쪽으로 가세요.

---

## 1. 축을 분리하라 🟡

| 축 | 질문 | 판정 |
|---|---|---|
| 형식 | **돌아가는가** | 스크립트가 답함 |
| 내용 | **맞는가** | 사람(에이전트)의 판단 |

합격선이 통과해도 내용이 틀릴 수 있고, 내용이 맞아도 합격선이 막을 수 있습니다. 한 에이전트에 맡기면 **객관적으로 확인되는 쉬운 쪽만 보고 통과**시킵니다.

각 에이전트 정의에 **"보지 않는 것"**을 명시하세요.

## 2. 분리의 대가 — 무주공산 🟢

축을 나누면 **어느 축에도 안 속하는 항목**이 생깁니다. 실제로 이런 것들이 방치됐습니다:

| 무주공산 | 왜 아무도 안 보나 |
|---|---|
| 계획된 항목이 실제로 생성됐는가 | 검토 대상이 "생성된 것"뿐이었다 |
| 이름·메타데이터가 계획과 일치하는가 | 내용 오류 아님 + 합격선 통과함 |
| 연출·표현 품질 | 어느 축도 아님 |

**대응:** 축을 나눈 뒤 **"이 항목은 누가 보는가"를 항목별로 한 번 훑으세요.** 답이 없는 것이 무주공산입니다. 대개 교차 대조 담당(형식 쪽)에 *"합격선이 강제하지 않는 규약도 대조하라"*로 붙이고, **차단이 아니라 보고**로 처리하면 됩니다.

### 계획 대비 누락 대조는 반드시 명시 배정 🟢

산출물만 검토하는 체계는 **"없는 것"을 구조적으로 못 봅니다.**

실제 피해: 계획된 항목 하나가 승인 대기로 빠졌는데, **그것을 근거로 삼는 다른 산출물이 순환 서술**이 됐습니다. 합격선은 번호 공백조차 말해주지 않고, 내용 검토자는 생성된 파일만 봅니다.

```bash
# 계획 목록은 계약 문서의 해당 표 행에서만 뽑을 것 (본문 언급이 섞인다)
awk '/^## {{계획 표 제목}}/{f=1;next} /^## /{f=0} f && /^\|/' {{계약파일}} \
  | grep -oE '{{파일 패턴}}' | sort -u > /tmp/planned.txt
ls {{산출 디렉토리}} | sort -u > /tmp/made.txt
comm -23 /tmp/planned.txt /tmp/made.txt   # 계획됐는데 없음 ← 이 방향만
```

역방향(파일은 있는데 계획에 없음)은 기존 자산이 전부 걸리니 보지 마세요.

## 3. 각각은 옳은데 겹쳐서 생기는 구멍 🟢

무주공산보다 찾기 어렵습니다. **어느 결정도 틀리지 않았는데 결과적으로 구멍**이 납니다.

실제 사례: 어떤 항목을 "형식으로 표현 불가"라 만들지 않기로 했고(옳음), 그것을 다루는 다른 항목은 별개 사유로 보류됐습니다(옳음). 겹치면서 **그 용어를 설명하는 산출물이 하나도 안 남았습니다.**

각 결정 시점에는 안 보입니다. 다른 결정을 아직 모르니까요.

**대응:** 검증에 *"출고물이 언급하는 개념 중, 그것을 설명하는 산출물이 하나도 없는 것"*을 찾는 항목을 넣으세요.

## 4. 경계면 교차 비교 🟢

파일이 각각 멀쩡해도 **경계에서** 깨집니다. 참조 id와 실제 파일명의 불일치는 하나씩 읽어서는 안 보입니다. 양쪽 목록을 뽑아 차집합을 구해야 보입니다.

**"존재 확인"이 아니라 "교차 비교"입니다.**

## 5. 합격선이 exit 0을 내도 정상이 아닐 수 있다 🟢

실제 사례: 참조 id가 치환 규칙에 걸려 링크 **생성 자체가 안 됐고**, 검증기는 "생성된 링크"를 대조하므로 **검사 대상에도 없었습니다.** exit 0이 나오고 화면은 깨져 있었습니다.

**합격선이 무엇을 검사하는지가 아니라, 무엇을 검사할 기회조차 없는지를 물으세요.**

## 6. 범위를 신규·변경분으로 한정 🟢

기존 자산이 이미 규약을 위반하고 있으면(실측: 22개 중 14개, 63%) 매번 같은 줄이 쏟아져 **신규 위반 1건이 묻힙니다.**

```bash
git diff --name-only HEAD -- {{경로}} ; git ls-files -o --exclude-standard {{경로}}
```

기존 위반은 별도 정리 과제로 분리하세요. **매번 나오는 경고는 곧 아무도 안 읽습니다.**

## 7. 판정이 갈리는 경계에 선을 그어라 🟢

"엄격하게"와 "과하게 요구하지 마라"가 부딪히는 지점에 기준이 없으면 검토자마다 판정이 갈립니다.

실제로 그은 선: **문장이 문자 그대로 거짓이면 수정필요, 증명을 생략한 것이면 통과.**

도메인에 맞는 선을 하나 정해 역할 정의에 박아두세요.

---

## 검증 설계 체크리스트

```
[ ] 축 분리 (합격선이 있을 때만) + 각 에이전트에 "보지 않는 것"
[ ] 항목별 "누가 보는가" 훑기 → 무주공산을 교차대조 담당에 배정
[ ] 계획 대비 누락 대조를 명시적으로 배정
[ ] "옳은 결정 둘이 겹쳐 생긴 구멍" 점검 항목
[ ] 경계면 교차 비교를 스크립트로
[ ] 합격선이 "검사할 기회조차 없는" 실패 유형 찾기
[ ] 점검 범위를 신규·변경분으로 한정
[ ] 판정 경계선을 하나 명문화
[ ] 절차에 지시가 아니라 실행 명령을 쓰고, 그 명령을 직접 돌려보고 넣기
```

마지막 항목이 특히 중요합니다. *"의존을 확인하라"*만 적으면 방법이 없어 눈대중이 됩니다. 그리고 **돌려보지 않고 넣은 명령은 거의 항상 어딘가 틀립니다** — 실제로 넣어둔 명령이 과잉 매칭이었습니다.
