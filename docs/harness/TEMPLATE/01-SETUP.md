# 01 · 착수 전

여기서 걸러야 할 것을 놓치면 뒤가 전부 헛돕니다.

---

## 1. 도구 가용성 확인 🟢

하네스 프레임워크는 대개 **에이전트 팀**(팀원 간 직접 통신)을 기본 모드로 가정합니다. 그런데 그 도구가 없는 환경이 있고, **없어도 에러가 안 납니다.** 조용히 단일 실행으로 폴백하고 산출물은 멀쩡히 나옵니다.

```
ToolSearch 로 TeamCreate 검색 → 안 나오면 팀 모드 금지
```

없으면 처음부터 서브 에이전트(`Agent` 도구) 모드로 설계하세요. **계획된 단독 실행과 사고로 인한 단독 실행은 결과가 다릅니다.**

## 2. 객관적 합격선을 찾아라 🟡

**이게 이 뼈대의 가장 큰 가정입니다.**

| | |
|---|---|
| 있다 | 빌드·린트·타입체크·테스트·스키마 검증 — 스크립트가 통과/실패를 판정 |
| 없다 | 문서 품질·기획 타당성·디자인 — 사람 판단만 가능 |

**합격선이 있으면:** 그것만 전담하는 에이전트를 두세요. 판정이 주관적이지 않아 수정 루프의 종료 조건이 생깁니다.

**합격선이 없으면:** 만들 수 있는지 먼저 보세요(체크리스트를 스크립트화, 스키마 정의). **만들 수 없으면 이 뼈대의 축 분리(04)는 성립하지 않습니다.** 그 경우 검증은 사람이 하고, 하네스는 생성 단계만 담당하는 얕은 구조가 맞습니다.

## 3. "형식은 통과하는데 내용이 틀린" 구멍을 목록화 🟢

합격선이 있어도 만능이 아닙니다. **여기가 하네스가 실제로 값을 만드는 자리입니다.**

방법: 합격선이 검사하는 항목을 나열하고, 각각에 물으세요 — **"이걸 통과시키면서 틀릴 수 있는 방법은?"**

```
{{합격선 항목}} → 통과시키면서 틀리는 법: {{...}} → 대응: 에스컬레이션 / 별도 검증
```

실제 사례: 그래프 블록이 **있는지**만 검사하고 그 그래프가 **말이 되는지**는 안 봤습니다. 에이전트가 그럴듯한 값을 지어내면 빌드는 통과하고, 잘못된 내용이 그대로 출고됩니다.

**대응 원칙: "모르면 만들지 말고 멈추고 보고하라."** 틀린 산출물은 없는 산출물보다 나쁩니다.

## 4. 3자 하네스/플러그인 감사 🟢

읽지 않은 코드를 돌리지 마세요.

```bash
find . -type f ! -name '*.md'                        # 실행 코드가 있나
find . -type f -perm -u+x                            # 실행 권한
grep -rniE 'rm -rf|curl.*\|sh|sudo|token|api[_-]?key|\.env|bypassPermissions'
grep -rniE 'https?://'                               # 외부 네트워크 = 인젝션 표면
```

**그리고 문서가 언급한 것이 실재하는지 확인하세요.** 참조된 CI 워크플로·문서가 실제로 없는 경우가 있습니다 — 문서상 약속일 뿐 자동 감시 장치가 없다는 뜻이므로, 업스트림 변경 시 방치될 수 있다고 가정하고 채택하세요.

## 5. 중간 산출물을 `.gitignore`에 미리 넣기 🟢

하네스는 보통 작업 디렉토리에 중간 산출물을 쓰고 "보존하라"고 합니다. 미리 막지 않으면 커밋됩니다.

```gitignore
_workspace/
_workspace_prev/
```

## 6. 기존 자산을 실제로 열어보기 🟢

파일명과 디렉토리 구조로 추측하지 마세요. **메타데이터를 열어** 명명 관례·번호 체계·진행 상태를 확인하세요.

실제 사례: 신규 단원인 줄 알았는데 기존 항목이 이미 그 단원을 시작해 놓았고, 번호도 이어받아야 했습니다. 안 읽었으면 단원을 중복 생성했을 겁니다.
