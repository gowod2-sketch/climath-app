## 게이트 배치 🟡

**전부 멈추지 마세요.** 사람 한 명의 응답을 기다리느라 승인 불필요한 작업까지 섭니다.

| 에스컬레이션 유형 | 차단 범위 |
|---|---|
| 기존 자산 수정 대기 | **그것을 쓰는 산출물만** |
| 구조(단원·스키마) 신설 대기 | 그 구조에 속한 산출물 전부 |
| 표현 불가 (일부) | 없음 — 진행하되 반드시 보고 |
| **표현 불가 (전량)** | **전체** — 아래 참조 |
| 범위 결정 | 없음 — 기본값으로 진행 |

### "전량 불가"는 성격이 다릅니다 🟡

어떤 입력은 **하나도 성립하지 않을** 수 있습니다. 개별 산출물의 문제가 아니라 **형식으로 그 입력을 다룰 수 있느냐**의 문제이므로, 착수 전에 사람이 결정해야 합니다. 진행하면 전량 재작업입니다.

이 판정이 나오면 구제 범위와 비용을 **옵션별로 정리해** 올리세요.

### 보류 단위는 근거 사슬 🟡

A를 보류하면 **A를 근거로 인용하는 B도 함께 보류**해야 합니다. 근거가 없으면 출고된 쪽이 순환 서술이 됩니다.

이 의존은 링크가 아니라 **평문 문장에 숨어 있어 자동으로 안 잡힙니다.** 차단 목록을 정한 뒤 출고 예정 산출물의 본문이 보류 항목에 기대는지 한 번 훑으세요.

## description 작성 🟢

프레임워크는 트리거를 **적극적("pushy")**으로 쓰라고 합니다. 그대로 따르면 **무관한 작업 중에도 튀어나옵니다.**

범위 한정을 붙이세요:
```
"...에만 사용하고, {{유사하지만 아닌 것}}에는 사용하지 않는다"
```

그리고 **should-NOT-trigger 쿼리 3개**를 직접 써보고 걸리는지 점검하세요. 경계가 모호한 것이 좋은 테스트입니다 — "명백히 무관한 것"은 테스트 가치가 없습니다.

후속 키워드(재실행·수정·보완)는 반드시 넣으세요. 초기 실행 키워드만으로는 후속 요청이 트리거되지 않습니다.
