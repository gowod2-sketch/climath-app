# 하네스 감사가 찾아낸 앱 버그

**이 버그들은 하네스 스프린트가 만든 것이 아닙니다.** 기존 콘텐츠(수열의 극한 단원)에 이미 있던 것을 정합성 감사가 찾아냈습니다.

**전부 `build.py`가 exit 0을 냅니다.** 그래서 여태 아무도 몰랐습니다.

## 버그 1 — 팁 링크가 조용히 죽는다 · **수정됨 (커밋 918ebb2, 배포 완료)**

**증상:** 개념 03 p2, 개념 04 p1에서 화면에 `[[∑val|급수의 합]]`이 **대괄호째** 나오고 팝업이 뜨지 않습니다.

**원인:** `build.py`의 `prose()`가 링크를 파싱하기 **전에** `syms()`를 돌립니다.

```python
def prose(t):
    t = syms(t)                    # ← 여기서 'sumval' → '&#8721;val'
    t = re.sub(r'\[\[([a-z0-9_]+)\|([^\]]+)\]\]', link, t)   # ← 더 이상 매치 안 됨
```

`sum`이 `SYM` 테이블에 있어서, 팁 id `sumval`이 `&#8721;val`로 바뀝니다. 그러면 링크 정규식의 `[a-z0-9_]+`에 걸리지 않아 `<span class="term" data-t="...">`가 **생성되지 않습니다.**

**왜 빌드가 못 잡나:** 링크 검사가 `data-t="([a-z0-9_]+)"`를 찾아 tip 파일 존재를 대조하는데, 애초에 `data-t`가 안 만들어졌으니 검사 대상에 없습니다. "없는 팁 id"로도 안 걸립니다.

**영향 범위:** 팁 id에 `SYM` 문자열(`sum`, `oo`, `alpha`, `beta`, `...`, `->`, `-oo`, `<=`, `>=`, `!=`, `+-`)이 부분 문자열로 들어간 모든 링크. 현재 `sumval` 하나가 해당되고 개념 03·04에서 쓰입니다.

**탐지 명령** (빌드 후 실행):
```bash
python3 -c "
import json; d=json.load(open('mathuit/content-data.json'))
print([(p['no'],f) for p in d['pages'] for f in ('p1','p2') if '[[' in p.get(f,'')] or '죽은 링크 없음')"
```

**수정 완료:** `prose()`가 이제 `[[id|글자]]` 링크를 `syms()` 실행 **전에** 자리표시자(`\x00N\x00`)로 빼뒀다가 되돌린다. `build.py`의 `prose()` 함수 정의를 보면 확인할 수 있다.

## 버그 2 — 수식 안 기호 약어가 엔티티 코드로 노출 · **수정됨 (커밋 918ebb2, 배포 완료)**

**증상:** 개념 03·06·07·08·10의 수식에서 `∑`가 아니라 `&#8721;` 이라는 글자가 그대로 보입니다. 본문에서는 `-oo`가 `&minus;`로 깨집니다(개념 01 p2, `diverge`·`oscillate`의 oneline).

**원인:** `mathify()`가 `syms()`를 먼저 돌린 뒤 결과를 **문자 단위로** 순회합니다.

```python
def mathify(t):
    t = syms(t)            # 'sum' → '&#8721;'
    ...
    if c.isdigit() or c in '+=()[]|,.<>/&#;':
        out.append('<span class="m">%s</span>' % c)   # & # 8 7 2 1 ; 이 각각 span 으로
```

`&#8721;`의 각 문자가 개별 span에 갇혀 HTML 엔티티로 해석되지 못합니다. `index.html:258`이 `innerHTML`로 넣으므로 화면에는 `&#8721;`이 문자 그대로 나옵니다.

**수정 완료:** `mathify()`가 이제 문자 단위 순회 전에 `ENTITY = re.compile(r'&[#a-zA-Z0-9]+;')`로 엔티티 전체를 먼저 매치해 통째로 넘긴다.

## 버그 3 — 팁 팝업 스텝 캡션의 기호 약어가 엔티티 코드로 노출 (미수정, 2026-09-05 발견)

**증상:** `euler` 팁 팝업의 4번째 스텝 캡션 "한없이 커지면 e = 2.718...에 수렴해요"가 화면에 `2.718&#8943;`로 그대로 나온다(마침표 세 개가 사람 눈에 보이는 "…" 대신 엔티티 코드 문자열로 노출).

**원인:** 버그 2와 같은 계열이지만 다른 경로다. `build.py`의 `parse_tip()`은 스텝 캡션을 `syms(cells[3])`으로만 처리한다(`prose()`나 `mathify()`를 안 거친다) — 그래서 `...`가 `&#8943;`로 바뀐 문자열이 그대로 `content-data.json`에 들어간다. 화면 쪽 `index.html`의 `paintPop()`은 이 값을 `cap.textContent = s.caption`으로 꽂는데, **`textContent`는 HTML 엔티티를 해석하지 않는다** — `innerHTML`이 아니라서 `&#8943;`가 문자 그대로 보인다.

**왜 빌드가 못 잡나:** `check.py`는 `def`(oneline)만 검사하고 `steps[].caption`은 보지 않는다.

**영향 범위:** `## steps`의 caption에 `SYM` 문자열(`sum, oo, alpha, beta, ..., ->, <=, >=, !=, +-`)이 부분 문자열로 들어간 모든 팁. 실측으로는 현재 27개 팁 중 `euler` 1건뿐(다른 팁들은 캡션에 이런 약어를 안 씀).

**수정 방향 (제안, 미적용):** 둘 중 하나. (a) `index.html`의 `paintPop()`에서 `cap.textContent=` 대신 `cap.innerHTML=`로 바꾸면 엔티티가 해석된다(다만 caption에 다른 특수문자가 섞였을 때 안전한지 별도 확인 필요). (b) `build.py`의 caption 처리에서 syms() 대신 캡션 전용으로 사람이 읽는 유니코드 문자를 직접 쓰게 하고 syms()를 안 태운다.

## 버그 4 — 수식 조건절의 `<`가 HTML로 깨질 수 있다 (미수정, 2026-09-05 발견)

**증상:** 개념 02(`lim_{n->oo} r^n = 0 (|r| < 1)`)의 eqR에서 `<` 문자가 화면에 안 보이거나 그 뒤 내용이 깨질 수 있다.

**원인:** `mathify()`의 문자 단위 순회에서 `<`가 `c.isdigit() or c in '+=()[]|,.<>/&#;'` 조건에 걸려 `'<span class="m">%s</span>' % c`로 그대로 문자열에 박힌다 — 즉 생성되는 조각이 `<span class="m"><</span>`다. 이 결과를 `innerHTML`로 삽입하면 브라우저는 `<span class="m">` 다음에 오는 `<`를 텍스트가 아니라 **새 태그의 시작**으로 읽어 곧바로 이어지는 `/span>`과 합쳐 `</span>`로 해석해 버린다. 즉 span이 내용 없이 바로 닫히고, 보여줘야 할 `<` 문자 자체가 마크업에 먹혀 사라진다(더 심하면 이후 마크업 구조가 밀릴 수 있다).

**왜 빌드가 못 잡나:** `build.py`는 HTML로 실제 렌더링해 보지 않는다(문자열만 생성). `>`는 텍스트로 나타나도 안전해 같은 문제가 없다 — `<`만 위험하다.

**영향 범위:** `$$` 수식의 `lim_{...}` 뒤 부분(eqR)에 조건절 등으로 `<`가 직접 들어간 경우. 실측으로는 개념 02 1건. 이번 회차(c14, c17~c22)는 전부 확인했고 해당 없음.

**수정 방향 (제안, 미적용):** `mathify()`에서 `<`를 만나면 `&lt;`로 이스케이프해서 span에 넣는다(`>`는 그대로 둬도 안전하지만 대칭성을 위해 함께 이스케이프해도 무방하다).

## 부수 확인 — `$$` 수식 개수

`build.py`는 `re.search`로 **첫 번째** `$$`만 찾습니다. 수식이 2개여도 빌드는 통과하고, 두 번째 수식은 p2에 원문 그대로 노출됩니다. 현재 위반 콘텐츠는 없지만, "빌드가 막아줄 것"이라 기대하면 안 됩니다.
